## 简化:去掉无加速效果的批量层,并对齐标题新鲜度说明

对分层标题解析做了一次整体 review,结果落到三处改动。

### 1. 移除 `readTitleSnapshots` 批量层(实测不加速)

原实现把宿主批量 API 当作 L2 加速层。**实测否决**:同一份 238 会话的真实语料上

| 方式 | 耗时 |
|---|---|
| 逐个 `readTitle`(每会话 `load` + `fold` 整份日志) | 22,305 ms |
| 一次 `readTitleSnapshots`(单次 `projectMany`) | 22,567 ms |

**无差别** —— `projectMany` 每个会话仍要 `load` 整份日志再 `foldSessionTitle`,批量只是把 N 次
API 调用合成一次,不减少工作量。因此该层连同其从未被传入的参数一起删除;真正的加速只有两条:
宿主的零 I/O 投影缓存(0.1.7+,实测 **207 ms**)与本地缓存(命中 **3 ms**,`resolve(name)` **1 ms**),
对比旧实现的 **22.3 s/次且不缓存**。

分层现在是 **L0 本地缓存 → L1 宿主投影缓存 → L3 逐条读取 → L4 磁盘扫描**,每层仍按能力探测下落,
0.1.5 及以下宿主不受影响。

### 2. 标题新鲜度说明与实际行为对齐(契约变更)

`README` / `USAGE` / `BEST_PRACTICES` 此前都写着「每次解析现读最新标题、**改名即刻生效、绝不缓存**」。
引入缓存后该说法已不成立。三处统一改为:**标题读自缓存,改名在下一个标题检查点后生效**,并给出
24h 新鲜度上限;需要立刻点名刚改名的会话时用 `session_id`。

这是一次**有意的契约放宽**,换来从"每次枚举都逐会话读日志"到"零日志解码"的差别。

### 3. 测试

批量层相关断言改写为新语义(L1 miss → 仅为 miss 的那些会话各做一次单条读取,且不再触碰任何批量 API)。
其余覆盖不变:命中零读取、E1–E4 惰性失效、仅改文件不重解、跨重启持久化、L1 命中/无标题行即答案/
抛错不破坏枚举、pre-0.1.7 宿主经 L3 仍可用、按 id 零枚举、缓存文件损坏与版本不符容错。

全部 115 测试通过。
